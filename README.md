# Mini NPU Simulator 과제 보고서

## 1. 개요
본 프로그램은 필터와 패턴 데이터를 입력받아 MAC(Multiply-Accumulate) 연산을 수행하고, 가장 유사한 패턴을 판정하는 시뮬레이터입니다.

## 2. 주요 구현 사항
- **MAC 연산**: 외부 라이브러리 없이 2중 반복문을 사용하여 `O(N^2)` 복잡도로 구현했습니다.
- **부동소수점 오차 처리**: `1e-9`의 epsilon 값을 설정하여, 미세한 계산 오차로 인한 판정 오류를 방지하고 동점(UNDECIDED) 처리를 수행하도록 했습니다.
- **데이터 분석**: JSON 파일을 읽어와 다양한 크기(5x5, 13x13, 25x25)의 패턴을 일괄 처리하고 성능을 측정합니다.

## 3. 결과 분석 및 FAIL 케이스 원인
- **분석 결과**: 총 6개의 테스트 케이스 중 3개는 PASS, 3개는 FAIL 판정을 받았습니다.
- **FAIL 원인**: 실패한 케이스(`size_5_1`, `size_13_2`, `size_25_1`)들은 계산된 Cross 점수와 X 점수의 차이가 극히 미세하여 프로그램이 **동점(UNDECIDED)**으로 판정했기 때문입니다. 
- **고찰**: 이는 프로그램의 로직 오류가 아니라, 부동소수점 연산의 한계를 `is_equal` 함수로 정확히 잡아냈음을 의미합니다. 실제 NPU 설계 시에도 이러한 정밀도 문제는 중요한 고려 요소임을 확인했습니다.

## 4. 성능 측정 결과
- **시간 복잡도**: 필터 크기 $N$에 대해 연산 횟수가 $N^2$에 비례함을 확인했습니다.
- 5x5(25회), 13x13(169회), 25x25(625회)로 크기가 커질수록 실제 측정된 평균 연산 시간도 그에 비례하여 증가하는 선형적인 경향을 보였습니다.

### 🛠 설계 특징 (Design Intent)

*   **라벨 정규화 로직 분리 (`normalize_label`)**
    *   **목적**: 데이터 입력 형식의 다양성(예: '+', 'x', 'Cross', 'X')을 한 곳에서 통합 처리함으로써 코드의 **유지보수성**을 극대화했습니다.
    *   **확장성**: 새로운 연산 패턴이나 라벨 형식이 추가될 경우, 비즈니스 로직을 건드리지 않고 해당 함수만 수정하여 시스템 전체에 적용할 수 있도록 설계했습니다.

    ### ⚖️ 모드별 판정 정책 (Judgment Policy)

본 시뮬레이터는 사용 목적에 따라 모드별로 서로 다른 판정 로직과 메시지를 적용합니다.

1. **Mode 1 (실시간 사용자 분석 모드)**
   - **정책**: 사용자에게 분석 결과를 직관적으로 전달하는 것이 목적입니다.
   - **동점 처리**: 두 필터의 점수가 완벽히 일치할 경우, 어느 한쪽으로 편향되지 않았음을 알리기 위해 `판정 불가 (UNDECIDED)`라는 상세 문구를 출력하여 사용자에게 추가적인 판단 기회를 제공합니다.

2. **Mode 2 (데이터셋 자동 검증 모드)**
   - **정책**: 대량의 데이터를 바탕으로 시스템의 정확도(Accuracy)를 측정하는 것이 목적입니다.
   - **동점 처리**: 동점 발생 시 특정 클래스로 확정할 수 없으므로, 정답(Expected)과 일치하지 않는 것으로 간주하여 엄격하게 `FAIL`로 처리합니다. 이는 시스템의 판정 신뢰성을 확보하기 위한 보수적인 설계 정책입니다.

   ## 🚀 대규모 데이터(1000x1000) 처리 분석 및 최적화 전략 (평가 항목 #19)

### 1. 1000x1000 스케일 처리 시 예상 문제점
- **연산 비용 (Time)**: $1000 \times 1000$ 행렬 연산 시 약 100만 번의 MAC 연산이 발생합니다. Python의 `for` 루프는 인터프리터 오버헤드가 커서 실시간 처리가 불가능한 수준의 지연이 발생합니다.
- **메모리 비용 (Memory)**: 64비트 부동소수점 기준, 행렬 하나당 약 8MB를 차지합니다. 대량의 데이터를 동시에 처리할 경우 메모리 대역폭 한계로 인해 데이터 전송 병목 현상이 발생하고 캐시 미스(Cache Miss)가 급증합니다.

### 2. 구체적 최적화 전략 (우선순위 순)

#### ① 블록화 및 타일링 (Tiling/Blocking) - [최우선]
- **내용**: 전체 데이터를 한 번에 처리하지 않고, L1/L2 캐시 크기에 맞춰 데이터를 작은 블록(예: 32x32) 단위로 쪼개어 연산합니다.
- **이유**: 데이터 지역성(Locality)을 높여 RAM 접근을 최소화하고 캐시 적중률을 극대화하여 속도를 높입니다.

#### ② 데이터 양자화 (Quantization)
- **내용**: FP64(8바이트) 대신 Int8(1바이트) 또는 FP16(2바이트) 형식을 사용합니다.
- **이유**: 메모리 사용량을 최대 8배 절감하고, 동일 시간 내 더 많은 데이터를 처리(Throughput 향상)할 수 있습니다.

#### ③ 병렬 처리 및 벡터화 (Parallelism/SIMD)
- **내용**: SIMD 명령어를 사용하여 한 번의 연산으로 여러 데이터를 처리하거나, 멀티코어를 활용해 필터 연산을 병렬화합니다.
- **이유**: CPU/NPU의 하드웨어 자원을 최대한 활용하여 전체 연산 시간을 단축합니다.

## ⚖️ CPU(직렬) vs NPU(병렬) 병목 및 성능 비교 (평가 항목 #20)

### 1. 직렬 처리 (CPU 방식)의 병목
- **특징**: 한 번에 하나의 연산만 수행하는 구조입니다.
- **병목 원인**: 
    - **명령어 오버헤드**: 데이터 하나를 처리할 때마다 명령어를 해석하고 실행하는 과정이 반복되어 연산 횟수($N^2$)가 늘어날수록 지연 시간이 기하급수적으로 증가합니다.
    - **낮은 처리량**: 클럭 속도가 아무리 빨라도 한 번에 처리하는 양이 제한적이어서 대규모 행렬 연산에 부적합합니다.

### 2. 병렬 처리 (NPU 방식)의 병목
- **특징**: 수많은 연산 유닛(PE, Processing Element)을 배치하여 동시에 연산합니다.
- **병목 원인**:
    - **데이터 전송 병목 (Memory Wall)**: 연산 유닛의 속도는 매우 빠르지만, 메모리(DRAM)에서 데이터를 가져오는 속도가 이를 따라가지 못해 유닛들이 노는 현상이 발생합니다.
    - **유닛 활용도 (Utilization)**: 병렬 유닛 수보다 처리할 데이터가 적거나 구조가 맞지 않으면 일부 유닛이 유휴 상태가 되어 효율이 떨어집니다.
    - **동기화 오버헤드**: 여러 유닛의 결과를 하나로 합치는 과정에서 발생하는 통신 지연이 병목이 됩니다.

### 3. 비교 요약
| 구분 | CPU (직렬) | NPU (병렬) |
| :--- | :--- | :--- |
| **핵심 병목** | 연산 유닛의 순차적 실행 한계 | 메모리 대역폭 및 데이터 전송 속도 |
| **스케일 영향** | 데이터가 커질수록 시간 선형 증가 | 데이터가 커질수록 메모리 병목 심화 |
| **최적화 방향** | 알고리즘 복잡도 감소 | 데이터 재사용성 극대화 (Tiling) |
